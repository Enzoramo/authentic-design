Add an **Invoice search** screen within the existing left-navigation shell. Reuse the app’s system sans type, purple accent, 8px control radius, spacing, and current table density. Keep **Invoice** as the domain term throughout.

- **Layout:** page title, one search/filter toolbar, then the existing Invoice table. Keep invoice number, customer, and payment status visible using established table conventions; retain existing invoice columns and row actions. Follow the app’s existing navigation and table behavior at narrow widths.
- **Search:** visible label “Search invoices”; placeholder “Invoice number or customer”; action “Search”. Enter and the Search button submit the query. Match against invoice number or customer, then intersect those results with the selected payment status. Clearing the query retains the status selection.
- **Filter:** a labeled “Payment status” select with “All”, “Paid”, and “Unpaid”; default to “All”. Changing it refreshes results while retaining the query. A blank query applies only the status filter. Display a result count after each completed request.
- **Results:** preserve existing row height, cell padding, typography, and column alignment. Show textual “Paid” or “Unpaid” labels so status does not depend on color. Use the purple accent according to the app’s established action and selection roles.
- **Recovery:** retain the toolbar during loading and announce “Searching invoices…”. For zero matches, show “No invoices match your search” and “Clear search and filters”, which resets both controls. On failure, show “Couldn’t load invoices” with “Try again”, preserving entered values.
- **Accessibility:** use labeled native controls, visible keyboard focus, semantic table headers, and a polite announcement for the completed result count.

The task is finding an Invoice from a known number or customer; a compact toolbar above the familiar table keeps those criteria beside the results. The tradeoff favors continuity over a new visual direction. Brand constraints come from the supplied brief; interaction details above are proposed design decisions.
